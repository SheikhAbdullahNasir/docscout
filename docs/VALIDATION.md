## Record format

Each run records the following. Values that the app or captured result did not expose are marked unavailable; no request counts, coverage, or findings are inferred.

- Repository and canonical public GitHub URL
- Commit SHA and scan time
- Returned scan status and cache state
- Relevant coverage completeness for the tree, selected documents, local links, root npm scripts, and labeled issues
- GitHub request count, if returned by DocScout
- Runtime, marked as client-measured wall time when the app does not report one
- Documentation suggestions emitted and each manually inspected finding's classification
- Labeled-issue opportunity count and representative label evidence; labels do not establish that work is easy
- Corrections, limitations, and observations

For every inspected documentation finding, use one classification: **supported/useful evidence**, **intentional/generated/project-convention behavior**, **false positive**, or **inconclusive**. An empty finding list is recorded as zero suggestions in the checked scope, not as evidence that the repository has no problems.

### Historical request-count contract finding (resolved)

`PROJECT_SPEC.md` section 9 requires coverage to report request count. The recovery summary normalized the absent `scan` object to JSON `null`; the successful response itself omitted `scan`, so its request count cannot be recorded. This is a concrete contract mismatch, not an unobserved measurement.

The current path explains the omission:

- [`GitHubClient.getSnapshot`](../apps/server/src/github/client.ts#L204) adds `scan: { status: 'partial', githubRequests, warnings }` only when `budget.warnings.length` is nonzero (lines 210–212). A warning-free ready result returns without `scan`.
- [`RepositoryScanCoverage`](../packages/shared/src/index.ts#L244) models `githubRequests` only inside a type with `status: 'partial'`; [`RepositorySnapshotResult`](../packages/shared/src/index.ts#L270) makes `scan` optional.
- The snapshot route spreads that result into the response and passes `budget.requestsUsed` to [`boundBrowserResponse`](../apps/server/src/routes/repository.ts#L76). For a response within the browser size limit, [`boundBrowserResponse`](../apps/server/src/routes/browserBudget.ts#L23) returns the original response unchanged. It attaches request count only when it must mark the response partial for the browser-size limit.

At the time of the first four attempts, no correction had yet been made. The focused follow-up below corrected the response contract; this records the historical blocker and is not a current Phase 6C.1 blocker.

**Follow-up correction:** A Phase 6C.1 regression fix now includes the actual scan-budget request count on warning-free and partial successful responses, and the browser coverage panel displays it. Focused offline tests verified complete, partial, bounded, empty, and cached responses. Run 5 confirms the live complete response includes `scan.status: complete`, `scan.githubRequests: 20`, and `scan.warnings: []`. The earlier repository responses remain historical and their request counts remain unavailable.
